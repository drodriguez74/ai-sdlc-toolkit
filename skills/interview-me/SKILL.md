# Interview Me

## Overview

Surface the hidden assumptions, constraints, and criteria that a vague request
relies on. Stops when the spec can be stated without ambiguity.

## When To Use

When the user request is short, vague, or ambiguous. When stakeholders disagree.
When success criteria are not stated.

## Workflow

1. Ask one high-impact question at a time. Avoid multi-question dumps.
2. Cover, in this order: user, goal, constraints, scope, success criteria, validation.
3. After each answer, restate the implication and confirm.
4. Stop asking when the spec can be stated without hidden assumptions.
5. Produce a concise requirements summary.

## Evidence And Verification

- Restate the gathered requirements; ask the user to confirm or correct.
- Track which questions were asked and answered.

## Common Rationalizations

- "I can infer the rest" — inference is where projects go wrong.
- "Asking too much will slow us down" — one targeted question per turn is fast.

## Red Flags

- Multiple questions in one turn.
- Questions about implementation before goal is clear.
- Proceeding to spec with open questions.

## Output Contract

A short requirements summary: user, goal, constraints, scope, non-goals,
success criteria, validation approach.
